# Decisions

Sensible defaults chosen where the brief was open. Each can be revisited.

| #   | Topic                   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Why                                                                           |
| --- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| D1  | Roles                   | Many-to-many `UserRole` (PLAYER, ORGANISER, ADMIN). Every user is PLAYER. Admins can grant/revoke ADMIN and ORGANISER from the admin UI; the last remaining admin cannot be demoted. All role changes are audited and the user is notified.                                                                                                                                                                                                                                                                                                                             | Covers "admins can add new admins" and lets an organiser also play.           |
| D2  | Organiser scope         | `TournamentOrganiser` with per-permission flags (entries, draws, results, refunds). ADMIN implicitly has all.                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Tournament-scoped permissions from the brief.                                 |
| D3  | Sessions                | **Changed in Phase 1:** own small session module instead of Auth.js. Auth.js v5 has no stable release (npm: beta only) and its credentials provider forces stateless JWT sessions. Web: random 256-bit token in an `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` cookie; only its SHA-256 is stored in `UserSession`, so logout/revoke is immediate. Mobile: 15-min HS256 access JWT (`AUTH_SECRET`) + rotating refresh token with reuse detection on the same `UserSession` table. OAuth/magic link can be added later (e.g. with Arctic) without changing sessions. | Revocable sessions shared by web and mobile, no beta dependency.              |
| D4  | Member number           | Generated from a Postgres sequence, format `TE` + 6 digits (e.g. `TE100245`). Login accepts email or member number (case-insensitive).                                                                                                                                                                                                                                                                                                                                                                                                                                  | Short, typeable, unique.                                                      |
| D5  | Player without account  | `PlayerProfile.userId` is optional, so admins can add/import players (and partners can be invited by email) before they sign up; on sign-up the profile is claimed by matching verified email / member number.                                                                                                                                                                                                                                                                                                                                                          | Needed for CSV import and partner invites.                                    |
| D6  | Registration shape      | `Registration` = one entry in an event (single player or pair); `RegistrationParticipant` = each player in it. One active entry per player per event via partial unique index (raw SQL).                                                                                                                                                                                                                                                                                                                                                                                | Doubles capacity counts pairs, not players.                                   |
| D7  | QR check-in             | Check-in token per participant (not per registration) so each doubles partner checks in individually.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Real tournament desks check in people.                                        |
| D8  | Payments                | Stripe **PaymentIntents** as the core; web uses Checkout or Payment Element, mobile uses Payment Sheet. One `Order` per checkout, `OrderItem` per participant share. Fees in integer cents.                                                                                                                                                                                                                                                                                                                                                                             | Same backend for web + mobile; per-partner payment.                           |
| D9  | VAT                     | `vatRateBasisPoints` per tournament, default 0. Many Dutch sports-association entry fees are VAT-exempt; organiser sets it. **Verify with an accountant.**                                                                                                                                                                                                                                                                                                                                                                                                              | Avoid guessing tax rules.                                                     |
| D10 | Federation rules        | Age categories and level classes are database rows (`AgeCategory`, `LevelClass`) seeded with placeholders (U11–U19, Senior, 35+…; A–D). Age is calculated on a configurable reference date (default 1 January of the tournament year). **Verify against Badminton Nederland regulations.**                                                                                                                                                                                                                                                                              | Brief says keep these configurable.                                           |
| D11 | Gender                  | `MALE`, `FEMALE`, `OTHER`. Event eligibility follows discipline (HE/HD male, DE/DD female, GD one of each); `allowOtherGender` per event lets organisers admit OTHER.                                                                                                                                                                                                                                                                                                                                                                                                   | Inclusive but compatible with gendered events.                                |
| D12 | Translatable content    | Organiser-written text (descriptions, news, venue notes) stored as JSON `{ nl, en? }`, falling back to nl. Proper names (tournament, venue, club) are single strings.                                                                                                                                                                                                                                                                                                                                                                                                   | Avoids parallel tables; simple to query.                                      |
| D13 | Standings               | Round-robin standings computed from matches, not stored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Single source of truth.                                                       |
| D14 | Court double-booking    | Postgres exclusion constraint on `CourtSlot` (btree_gist).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | DB-level guarantee.                                                           |
| D15 | Follow players          | `PlayerFollow` lets a user follow any public player and receive in-app/email (later push) notifications when their matches are scheduled or results are entered.                                                                                                                                                                                                                                                                                                                                                                                                        | User's requirement to follow fellow participants.                             |
| D16 | Minors                  | Under-16 profiles flagged `isMinor`; need a `PARENTAL_CONSENT` consent record; public profile defaults off; only name + club shown publicly.                                                                                                                                                                                                                                                                                                                                                                                                                            | GDPR / AVG data minimisation.                                                 |
| D17 | Background jobs         | pg-boss (runs on the same Postgres) rather than Vercel Cron.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Works the same on Vercel or Hetzner; retries built in.                        |
| D19 | Tooling versions        | Tailwind CSS v4 (CSS-first config, current shadcn/ui default), next-intl v4, Prisma 6, pnpm 11 (build-script allowlist in `pnpm-workspace.yaml` → `allowBuilds`; packages younger than 24 h are refused by default), Vitest 4, ESLint 9 flat config. No separate `packages/config`: one `tsconfig.base.json` plus a small ESLint config per package.                                                                                                                                                                                                                    | Fewer moving parts.                                                           |
| D20 | Password hashing        | `@node-rs/argon2` (argon2id). Prebuilt binaries, no native compiler needed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Meets "argon2" requirement, works on Intel/ARM Mac and Linux.                 |
| D21 | Shared packages         | `packages/shared` and `packages/db` export TypeScript source and are compiled by Next.js (`transpilePackages`), not built separately.                                                                                                                                                                                                                                                                                                                                                                                                                                   | No build step for internal packages.                                          |
| D22 | Env loading             | One `.env` at the repo root, loaded by `dotenv-cli` in package scripts. Validated with Zod in `apps/web/src/env.ts`, lazily so builds don't need a database.                                                                                                                                                                                                                                                                                                                                                                                                            | One place to configure.                                                       |
| D23 | Phase 0 links           | Home page buttons for "browse tournaments" / "create account" are shown disabled ("coming soon") until Phases 1 and 3 add the pages.                                                                                                                                                                                                                                                                                                                                                                                                                                    | No dead links.                                                                |
| D24 | Dependency overrides    | `pnpm-workspace.yaml` overrides force patched `postcss` (Next.js 15.5 pins 8.4.31) and `deepmerge-ts` 8 (Prisma 6 pins 7.x). Remove when the parents ship fixes. Accepted: `braces` ≤3.0.3 (high, ReDoS) inside `eslint-config-next` — no fixed release exists and it only runs during linting. Dependabot (2-day cooldown, matching pnpm's 24 h rule) watches for new advisories.                                                                                                                                                                                      | Audit 15 → 1 advisory (2026-10-17); none reach the request path.              |
| D25 | Content-Security-Policy | Baseline CSP on every response: only our origin for scripts/styles/images/fonts/API calls, no plugins, no framing, `form-action 'self'`. Scripts need `'unsafe-inline'` for Next.js' inline bootstrap; a nonce-based strict policy plus Stripe/Sentry/R2/map origins comes in Phase 8.                                                                                                                                                                                                                                                                                  | Limits what an XSS bug could load or send, without breaking static rendering. |
| D26 | Test environment        | https://test.tourneasy.app on Hostinger Web Apps (Node.js, preset Other, standalone server) with Neon Postgres (eu-central-1). Auto-deploys from `main`. See `docs/deploy-test.md`.                                                                                                                                                                                                                                                                                                                                                                                     | Hostinger plan already owned; Neon gives EU-hosted Postgres.                  |
| D27 | Rate-limit table        | `RateLimitBucket` (from the earlier untracked draft) is now a proper model and migration. Fixed windows in Postgres: login 30/15 min per IP and 10/15 min per identifier, sign-up 10/h per IP, password reset 10/h per IP and 3/h per email. 5 wrong passwords lock the account for 15 min.                                                                                                                                                                                                                                                                             | Works across instances without Redis.                                         |
| D28 | Sign-up fields          | Follows the front-end brief (first/last name, mobile, email, gender, preferred events as checkboxes) **plus date of birth**, which the original brief needs for age categories and the under-16 parental-consent rule. Mobile is required at sign-up.                                                                                                                                                                                                                                                                                                                   | Both briefs satisfied.                                                        |
| D29 | Email delivery          | `EMAIL_TRANSPORT` = `smtp` (Mailpit locally, any provider in production) or `log` (prints emails incl. links to the server log; test server until SMTP is configured) or `memory` (tests). Plain inline-styled HTML templates from the shared nl/en texts; React Email in Phase 7. Login is allowed before email verification; tournament entry (Phase 4) will require it.                                                                                                                                                                                              | Test server works without a mail provider.                                    |
| D30 | Privacy by default      | New players are **not** listed publicly until they opt in on their profile (GDPR art. 25); under-16s can never be public. Account deletion anonymises personal data, keeps the birth year for age-category history, revokes all sessions, and is refused for the last admin.                                                                                                                                                                                                                                                                                            | Data minimisation.                                                            |
| D31 | Account enumeration     | Login and password reset never reveal whether an account exists (same error, same timing via a dummy hash check). Sign-up does report a taken email address — the usual trade-off for a usable form.                                                                                                                                                                                                                                                                                                                                                                    | Balanced security and usability.                                              |
| D32 | Deferred from Phase 1   | Profile photo upload (needs R2 storage, Phase 2), OpenAPI document generation (Phase 3, once more endpoints exist), changing the email address (needs re-verification flow), magic-link login (optional in brief).                                                                                                                                                                                                                                                                                                                                                      | Keep Phase 1 focused.                                                         |
| D33 | Front-end design        | Visual design is handled in a separate chat/brief (`Front end/`, git-ignored here). Phase 1 pages use the existing tokens and are built to be restyled without logic changes.                                                                                                                                                                                                                                                                                                                                                                                           | Parallel design work.                                                         |
| D18 | Hosting default         | Hetzner (Germany/Finland) with Docker, or Vercel + Neon EU — chosen at Phase 8. Development fully in Docker.                                                                                                                                                                                                                                                                                                                                                                                                                                                            | EU data residency either way.                                                 |
